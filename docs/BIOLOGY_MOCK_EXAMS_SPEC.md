# BIOLOGY MOCK EXAMS — IMPLEMENTATION SPEC

## 0. Цель

Реализовать полноценный режим пробников ЕГЭ по биологии поверх уже существующих уроков, банка вопросов и режима «По заданиям ЕГЭ». Пользователь должен иметь возможность пройти целый экзаменационный вариант в условиях, максимально близких к реальному ЕГЭ, сохранить/продолжить попытку, завершить её, получить корректный результат, подробный разбор и карту слабых мест.

Это не «ещё одна тренировка на 28 случайных вопросов». Нужен отдельный экзаменационный workflow с фиксированным вариантом, сохранением состояния, таймером, навигацией по заданиям, запретом подсказок до завершения, корректным подсчётом баллов и полноценным post-exam review.

Текущая основа проекта уже включает:
- `content/biology/course.json` с существующими уроками и вопросами;
- `content/biology/exam-lines.json` с 28 линиями ЕГЭ;
- line-mode API/UI;
- существующие attempts/progress/reveal механики;
- вопросы разных типов, включая `extended_answer`, эксперименты, графики, таблицы, генетические задачи и задания с медиа.

Пробники обязаны переиспользовать эту инфраструктуру, а не дублировать контент.

## 1. BEFORE-аудит обязателен

До реализации:

1. Проанализировать актуальную структуру `exam-lines.json` и банка вопросов.
2. Для каждой из 28 линий определить количество пригодных для пробника вопросов.
3. Найти линии, где:
   - слишком мало вопросов;
   - вопросы повторяют друг друга;
   - отсутствует нужная сложность;
   - есть broken media;
   - отсутствуют корректные объяснения/критерии;
   - тип ответа не позволяет надёжно работать в экзаменационном режиме.
4. Составить краткий BEFORE-report в `content/biology/MOCK_EXAM_AUDIT.md`.
5. Если какая-то линия не может стабильно участвовать в генерации нескольких полноценных вариантов, точечно расширить банк оригинальными вопросами. Не делать массовую шаблонную генерацию.

Нельзя скрывать дефицит банка случайными повторами одного и того же вопроса.

## 2. Формат пробника

Каждый полноценный пробник должен содержать ровно один слот для каждой актуальной экзаменационной линии из `exam-lines.json` в официальном порядке.

Источник истины по количеству линий, part, answerFormat и структуре — `exam-lines.json`, а не захардкоженные числа в UI/сервере. На текущем состоянии ожидается 28 линий.

Для каждой позиции хранить:
- `line`;
- `questionId` / стабильный question key;
- порядковый номер;
- part;
- max primary score для этой позиции;
- answer format;
- media refs, если есть.

Вариант после создания фиксируется. При перезагрузке нельзя заново выбирать другие вопросы.

### Генерация варианта

Алгоритм должен:
- брать только вопросы с корректным `examLine`;
- не использовать один вопрос дважды в одном варианте;
- по возможности избегать повторения недавних вопросов пользователя из предыдущих пробников;
- сохранять равномерное предметное покрытие там, где одна линия допускает несколько тем;
- учитывать difficulty, чтобы вариант не состоял только из лёгких или только из экстремально сложных авторских вопросов;
- быть детерминируемым через stored variant/seed после создания;
- не менять старый вариант после обновления банка.

Если для конкретной линии недостаточно валидных вопросов, генератор должен fail-safe сообщить об этом разработчику/audit, а не подставлять вопрос от другой линии.

## 3. Режимы

Нужно как минимум два пользовательских режима.

### А. Полный пробник

Экзаменационный режим:
- все линии;
- таймер;
- без мгновенной проверки;
- без `Не знаю — показать разбор` до завершения;
- без правильных ответов и explanation в API payload до сдачи;
- ответы можно менять до отправки;
- можно помечать задания «вернуться позже»;
- можно переходить между заданиями в любом порядке;
- сохраняется автоматически.

### Б. Пробник без таймера

Та же структура и оценивание, но без жёсткого обратного отсчёта. Нужен для первых диагностик.

Не смешивать этот режим с обычной тренировкой.

## 4. Таймер и состояние попытки

Продолжительность экзамена должна быть конфигурируемой в metadata/config, а не размазана magic-number по frontend/backend. Если в проекте нет подтверждённой официальной длительности для выбранного exam year/sourceVersion, использовать явно помеченную конфигурацию и не выдавать её как неизменный норматив.

Состояние попытки хранить на сервере/в БД:
- `id`;
- `user_id`;
- `subject`;
- `exam_year`;
- `source_version`;
- `mode`;
- `status`: `in_progress | submitted | expired`;
- `started_at`;
- `submitted_at`;
- `duration_seconds`;
- `variant_seed` или immutable task mapping;
- список заданий;
- ответы пользователя;
- flags «вернуться»;
- elapsed/remaining timing data;
- итоговые баллы после submission.

Нельзя доверять только браузерному таймеру. После reload пользователь должен видеть корректное оставшееся время.

При истечении времени:
- попытка автоматически переводится в завершённую;
- сохранённые ответы учитываются;
- незаполненные остаются пустыми;
- нельзя после этого менять ответы.

Автосохранение ответа — сразу или с коротким debounce, с понятным визуальным статусом `Сохранено`.

## 5. UI пробника

### Экран запуска

Показывать:
- «Пробник ЕГЭ по биологии»;
- режим: полный / без таймера;
- количество заданий;
- краткое объяснение правил;
- кнопку `Начать пробник`;
- если есть незавершённая попытка — `Продолжить` и отдельно возможность начать новый вариант только через понятное подтверждение.

### Экран экзамена

Desktop и mobile friendly.

Обязательно:
- номер текущего задания;
- part/линия при необходимости без лишнего учебного спойлера;
- условие;
- медиа;
- поле/контролы ответа по типу задания;
- `Назад` / `Далее`;
- палитра 1…N;
- состояния палитры: не отвечено / отвечено / помечено;
- таймер в timed mode;
- кнопка `Завершить пробник`;
- confirmation modal с количеством незаполненных заданий.

Не показывать во время пробника:
- правильный ответ;
- explanation;
- common mistakes;
- scoringPoints;
- «показать разбор»;
- XP за отдельное задание;
- индикатор правильно/неправильно после ответа.

### Mobile

Проверить минимум 360–430 px:
- палитра не должна ломать экран;
- таймер остаётся видимым, но не перекрывает контент;
- таблицы/схемы скроллятся корректно;
- большие ответы второй части удобно вводятся;
- submit controls доступны без горизонтального overflow.

## 6. Типы ответов

Использовать существующие question types и trainer mechanics, но в exam-shell.

Первая часть:
- selectable/multiple answer;
- matching;
- sequence;
- numeric/text short answer;
- table/image/graph и другие существующие типы.

Вторая часть / развёрнутые ответы:
- пользователь вводит полный текст;
- ответ сохраняется как часть экзамена;
- после submission показываются эталон, `scoringPoints`, `commonMistakes` и критерии;
- нельзя притворяться, что свободный биологический ответ автоматически оценён без надёжного механизма.

Если в проекте нет настоящей semantic/manual grading системы, итог должен иметь два уровня:
1. `Автоматически проверено` — задания с однозначным ответом;
2. `Требует проверки по критериям` — extended answers.

Для extended answers после сдачи реализовать удобную самопроверку по критериям:
- показать пункты критерия;
- пользователь отмечает выполненные пункты/выставляет допустимый первичный балл;
- после этого пересчитывается `provisional primary score`;
- явно маркировать его как результат самопроверки, а не официальный автоматический балл.

Не выдавать ложную точность.

---

## 7. Оценивание

### Первичные баллы

Оценивание должно быть data-driven.

Для каждого вопроса/линии определить max primary score и правила scoring. Нельзя предполагать, что каждое задание = 1 балл.

Поддержать partial credit там, где текущая экзаменационная механика и question data это допускают.

Хранить:
- `auto_primary_score`;
- `manual_or_self_score` для extended;
- `primary_score_total`;
- `primary_score_max`;
- число выполненных/не выполненных;
- score по линиям.

### Вторичный/тестовый балл

Не хардкодить неофициальную шкалу 2027.

Если в репозитории нет подтверждённой текущей официальной шкалы перевода, показывать первичный результат как основной, а тестовый балл либо:
- не показывать;
- либо показывать только через versioned scale с явным source/version.

Нельзя выдумывать перевод первичных баллов в 100-балльную шкалу.

---

## 8. Результат после сдачи

После submission пользователь видит отдельный экран результата.

Обязательно:
- первичный балл / максимум;
- статус проверки второй части;
- сколько заданий выполнено;
- сколько правильно / частично / неправильно / не отвечено;
- время прохождения;
- результат по каждой линии;
- результат по крупным разделам биологии;
- слабые линии;
- слабые темы;
- кнопка `Разобрать ошибки`;
- кнопка `Пройти новый пробник`;
- ссылка обратно в режим «По заданиям ЕГЭ» для слабой линии.

### Разбор

Для каждого задания после сдачи:
- условие;
- ответ пользователя;
- правильный ответ / эталон;
- начисленные баллы;
- explanation;
- scoringPoints для extended;
- commonMistakes;
- ссылки на связанные уроки;
- ссылка `Потренировать линию N`.

Для неверных заданий автоматически формировать список повторения, но не менять существующую модель прогресса агрессивно.

## 9. История пробников

В профиле или разделе `Пробники` нужна история попыток:
- дата;
- режим;
- статус;
- первичный балл;
- максимум;
- duration;
- кнопка открыть результат;
- незавершённый пробник — `Продолжить`.

Хранить старые варианты неизменными, даже если контент позже обновился.

Показывать динамику минимум последних попыток простым списком/мини-графиком без тяжёлых зависимостей.

## 10. Backend/API

Спроектировать endpoints в стиле текущего сервера, например:
- `GET /api/subjects/biology/mock-exams` — история/active attempt;
- `POST /api/subjects/biology/mock-exams` — создать попытку;
- `GET /api/subjects/biology/mock-exams/:id` — получить экзаменационный payload;
- `PATCH /api/subjects/biology/mock-exams/:id/answers` — сохранить ответ/flag;
- `POST /api/subjects/biology/mock-exams/:id/submit` — завершить;
- `GET /api/subjects/biology/mock-exams/:id/result` — результат/разбор;
- отдельный endpoint/patch для self-scoring extended answers при необходимости.

Названия можно адаптировать под архитектуру проекта.

Критично:
- ownership check: пользователь видит только свои попытки;
- submitted attempt immutable кроме разрешённой post-exam self-score части;
- correct answers не возвращаются до submission;
- повторный submit idempotent;
- повторное сохранение того же ответа безопасно;
- нельзя подменить question id, не принадлежащий варианту;
- нельзя начислять лишние XP/attempts повторными запросами.

## 11. DB/migrations

Добавить минимально необходимые таблицы/поля через обычные migrations проекта.

Рекомендуемая модель:
- mock_exam_attempts;
- mock_exam_items;
- mock_exam_answers или JSON answer storage, если это согласуется с текущим DB abstraction.

Сохранять stable question identity и snapshot минимум тех данных, которые нужны для честного исторического результата. Не хранить plaintext sensitive data.

PostgreSQL и SQLite test mode должны работать одинаково через существующий `src/db.js` abstraction.

Не ломать existing auth/session/progress/training.

## 12. Контентная честность и качество варианта

Нельзя:
- копировать коммерческие банки;
- массово копировать задания ФИПИ;
- превращать пробник в случайный набор авторских задач без соответствия линии;
- автоматически менять examLine старых вопросов без проверки смысла;
- давать пользователю правильный ответ через API до завершения;
- считать extended answer автоматически правильным по совпадению пары слов;
- показывать фиктивный «балл ЕГЭ 87/100», если шкала не подтверждена.

Новые вопросы, если необходимы, должны быть оригинальными, но повторять экзаменационную механику.

## 13. Audit script

Добавить `scripts/audit-biology-mock-exams.js` и npm script `audit:biology-mocks`.

Проверки минимум:
- registry линий доступен;
- каждая линия имеет пригодные вопросы;
- question refs существуют;
- все mock-eligible questions имеют валидный examLine;
- отсутствуют duplicate question IDs/keys;
- media refs существуют;
- scoring metadata валидны;
- extended answers имеют scoringPoints/commonMistakes;
- generator может собрать полный вариант без дубликатов;
- минимум несколько разных seeds создают валидные варианты;
- каждый вариант покрывает все линии ровно один раз;
- answer leak check;
- submitted attempt immutable;
- ownership check;
- expired timer behavior;
- self-score не может превысить max score.

Audit не должен объявлять качество вопросов хорошим только по counts. Counts — только structural sanity.

## 14. Тесты

Добавить regression/integration tests минимум на:

1. создание полного пробника;
2. все линии присутствуют ровно один раз;
3. два разных варианта не обязаны быть идентичными;
4. reload возвращает тот же fixed variant;
5. correct answer/explanation не утекли до сдачи;
6. сохранение ответа;
7. изменение ответа до submission;
8. flags;
9. submit;
10. idempotent повторный submit;
11. после submit ответ менять нельзя;
12. scoring первой части;
13. extended answer требует post-exam criteria/self-score, если нет реального grader;
14. self-score ограничен диапазоном;
15. таймер/expired attempt;
16. пользователь B не видит попытку пользователя A;
17. history;
18. deep links результата;
19. существующие training/line-mode endpoints не сломаны;
20. SQLite tests и PostgreSQL-compatible SQL.

## 16. Acceptance criteria

Задача считается выполненной только если:

- есть отдельный пользовательский раздел `Пробники`;
- создаётся полноценный фиксированный вариант по всем линиям;
- вариант сохраняется между reload;
- timed/untimed режимы работают;
- правильные ответы не текут до submission;
- ответы и flags сохраняются;
- есть безопасный submit и auto-expire;
- scoring data-driven;
- extended answers не получают фиктивную автоматическую оценку;
- после сдачи есть полный разбор и ссылки на слабые линии/уроки;
- история пробников работает;
- пользователь не может читать/менять чужую попытку;
- все медиа открываются;
- mobile не ломается;
- audits/tests зелёные;
- существующие training, progress, reveal и line-mode не сломаны.

## 17. Финальный отчёт Codex

В финале дать отчёт строго по разделам:

A. BEFORE audit и найденные gaps.

B. Архитектура пробников и DB changes.

C. Генератор вариантов и правила выбора вопросов.

D. UI/UX: запуск, экзамен, таймер, navigation palette, mobile.

E. Scoring и extended answers.

F. Result/review/history.

G. Безопасность/API invariants и отсутствие answer leak.

H. Все запущенные проверки с точными результатами + что не удалось выполнить.

Не считать задачу готовой только потому, что созданы таблицы/API. Готовность определяется реальным end-to-end пользовательским сценарием.
