# BIOLOGY — режим «По линиям ЕГЭ»

## Статус документа

Каноническое ТЗ на реализацию второго маршрута подготовки по биологии: не только «по темам», но и «по заданиям/линиям ЕГЭ».

Экзаменационная версия: **ЕГЭ-2027, проект ФИПИ**. До публикации финальных документов 2027 нельзя называть проект окончательной версией. Первичный источник структуры экзамена — ФИПИ. Существующую теорию и банк заданий ОСНОВЫ не дублировать: line-mode должен связывать уже созданные уроки, схемы и вопросы через метаданные.

---

# 1. Цель

На странице «Биология» пользователь должен иметь два равноправных способа подготовки:

1. **По темам** — существующий маршрут по разделам/темам/урокам.
2. **По заданиям ЕГЭ** — новый маршрут по номерам экзаменационных линий.

Пример пользовательского сценария:

`Биология → По заданиям ЕГЭ → Задание 23 → Что проверяют → Нужная теория → Как решать → Ловушки → Разобранные примеры → Тренировка → Ошибки/прогресс`.

Ключевой принцип: теория хранится **один раз**. Line-mode не создаёт копии уроков. Он строит экзаменационный маршрут поверх существующей структуры.

---

# 2. Что нельзя делать

- Нельзя создавать 28 копий теории внутри отдельных страниц линий.
- Нельзя вручную вставлять большие куски текста из существующих уроков в новый JSON только ради line-mode.
- Нельзя считать линию «готовой» только потому, что у неё есть `examLine` в одном вопросе.
- Нельзя показывать пустую страницу линии.
- Нельзя показывать технические ID/slugs, `EGE_REQUIRED`, `contentStatus`, audit-пометки и другие редакционные метки пользователю.
- Нельзя ломать существующие ID уроков/вопросов, прогресс, историю попыток и reveal-flow.
- Нельзя менять auth/пароли/сессии/ unrelated DB-логику без реальной необходимости.
- Нельзя массово копировать задания ФИПИ или коммерческих банков. Практика остаётся оригинальной; ФИПИ используется для структуры и механик.
- Нельзя путать «номер линии» и «тему»: одна линия может требовать знаний из нескольких разделов, а один урок может быть связан с несколькими линиями.

# 3. BEFORE-аудит

До изменения кода вывести фактическое состояние текущего `main`.

Для Biology собрать таблицу по всем существующим вопросам и урокам:

- номер линии (`examLine`);
- сколько вопросов с этой линией;
- типы вопросов;
- difficulty;
- какие lesson IDs/slugs покрывают линию;
- какие topics/sections связаны с этими уроками;
- сколько уроков напрямую или косвенно помечены этой линией;
- есть ли media/SVG;
- есть ли задания с пустым/невалидным `examLine`;
- есть ли линия, которая встречается в вопросах, но не связана с теорией;
- есть ли теория, которая должна быть доступна в line-mode, но не имеет экзаменационной привязки.

Отдельно проверить диапазон текущих номеров линий и не предполагать автоматически, что существующие данные идеальны.

BEFORE-аудит должен зафиксировать:

- `TOTAL BIOLOGY LESSONS`
- `TOTAL BIOLOGY QUESTIONS`
- `QUESTIONS WITH VALID EXAM LINE`
- `QUESTIONS WITHOUT EXAM LINE`
- `LINES PRESENT`
- `LINES WITH 0 QUESTIONS`
- `LINES WITH 0 THEORY LINKS`
- `ORPHAN LINE REFERENCES`

Если в текущем контенте есть противоречия в line mapping, исправить их в этой же задаче на основе актуальной структуры ФИПИ-2027 project и существующей предметной теории.

# 4. Экзаменационная модель данных

Нужен единый машиночитаемый реестр линий Biology.

Предпочтительный вариант — отдельный файл, например:

`content/biology/exam-lines.json`

Либо эквивалентная структурированная секция в существующем course manifest, если это лучше соответствует текущей архитектуре.

Для каждой линии минимум:

```json
{
  "line": 23,
  "title": "Работа с биологическим объектом или схемой",
  "part": 2,
  "answerFormat": "развёрнутый ответ",
  "shortDescription": "...",
  "skills": ["..."],
  "lessonRefs": ["stable-lesson-slug"],
  "questionRefs": ["stable-question-key"],
  "strategy": ["..."],
  "commonTraps": ["..."],
  "status": "verified"
}
```

Названия/описания должны быть ученическими, понятными, без канцелярита. При этом нельзя придумывать несуществующую официальную формулировку. Где уместно, писать «что обычно проверяет эта линия» вместо утверждения, что формулировка дословно официальная.

## 4.1. Источник связей

Связи должны строиться из:

- `lesson.examLines` / существующего эквивалента;
- `question.examLine`;
- тематической структуры курса;
- ручной верификации сложных межраздельных линий.

Если lesson-level line metadata отсутствует или неполна — добавить её аккуратно, сохраняя стабильные IDs/slugs.

## 4.2. Трансверсальные линии

Особое внимание линиям, которые не относятся к одному разделу.

Например:

- анализ таблиц/графиков/данных;
- эксперимент и методология;
- работа со схемами/изображениями;
- развёрнутые причинно-следственные задания;
- генетические/цитологические расчёты.

Такая линия должна связывать несколько релевантных уроков из разных разделов, а не открывать один случайный урок.

# 5. Пользовательский интерфейс

## 5.1. Biology landing

На главной странице Biology добавить явный переключатель/две карточки:

- **По темам**
- **По заданиям ЕГЭ**

Существующий тематический маршрут должен остаться полностью рабочим.

Переключатель должен быть очевиден на desktop и mobile.

## 5.2. Экран списка линий

Показать карточки всех актуальных линий экзамена в правильном порядке.

Каждая карточка:

- `Задание N`;
- краткое понятное название;
- часть экзамена;
- тип ответа/механика;
- количество доступных тренировочных заданий;
- прогресс пользователя по линии, если он авторизован;
- CTA `Открыть` / `Тренироваться`.

Не показывать внутренние IDs.

Не использовать огромные полотна текста на grid-экране.

## 5.3. Страница конкретной линии

Структура сверху вниз:

### A. Заголовок

- `Задание N`
- понятное название
- часть экзамена
- тип ответа

### B. «Что здесь проверяют»

Короткое объяснение навыка/механики, а не просто перечень тем.

### C. «Что нужно знать»

Список необходимых уроков/микротем, сгруппированный логично.

Каждый элемент ведёт на **существующий** lesson route.

Показывать:

- название урока;
- раздел;
- статус прогресса пользователя;
- при необходимости короткую подпись «зачем это для задания N».

### D. «Как решать»

Пошаговый алгоритм именно для механики линии.

Не писать универсальную пустую формулу вида «внимательно прочитайте условие». Алгоритм должен отражать конкретный экзаменационный навык.

### E. «Типичные ловушки»

Реальные ошибки ученика:

- неправильная единица анализа;
- путаница причины/следствия;
- неверное чтение осей;
- подмена процесса термином;
- отсутствие объяснения механизма во второй части;
- неправильная последовательность;
- неверное определение контрольной/экспериментальной группы;
- и т.д. — только релевантное конкретной линии.

### F. Разобранные примеры

Показывать несколько **оригинальных** заданий из существующего банка этой линии с полноценным разбором.

Правильный ответ не должен утекать до ответа/reveal.

### G. Тренировка

Кнопка запуска отдельной сессии, отфильтрованной по `examLine=N`.

Желательно варианты:

- `5 заданий`
- `10 заданий`
- `Все доступные`

Если банк мал, не показывать неработающие варианты.

### H. Прогресс

Для авторизованного пользователя:

- решено;
- правильных;
- accuracy;
- слабые связанные темы;
- последний результат;
- `Повторить ошибки`.

Для гостя — нормальный fallback без ошибки API.

# 6. Практика по линии

## 6.1. Повторное использование существующего trainer flow

Не писать второй независимый тренажёр, если текущий можно расширить фильтром.

Нужен route/state/filter вида:

`subject=biology&examLine=23`

или эквивалент.

Сессия должна брать только вопросы этой линии.

Сохраняются:

- attempts;
- progress;
- XP;
- reveal behaviour;
- «Не знаю — показать разбор»;
- scoring для extended answers;
- existing answer review.

## 6.2. Порядок вопросов

Не выдавать только один тип подряд, если линия допускает несколько механик.

Внутри линии желательно разнообразие difficulty и подтипов, но без искусственного рандома, ухудшающего качество.

## 6.3. Недостаток банка

Если у линии слишком мало заданий для нормальной тренировки, НЕ скрывать проблему.

В аудите отметить линию как `practice_gap` и добавить **небольшое целевое количество качественных оригинальных заданий**, только если это реально необходимо для работоспособного line-mode.

Не превращать задачу в массовую генерацию сотен вопросов.

---

# 7. Backend / API

Выбрать решение, соответствующее текущей архитектуре.

Нужны эквиваленты следующих возможностей:

- получить список Biology exam lines;
- получить одну линию с theory refs и доступным количеством questions;
- получить practice set по `examLine`;
- получить user progress/statistics по line.

Примерно:

- `GET /api/subjects/biology/exam-lines`
- `GET /api/subjects/biology/exam-lines/:line`
- existing questions endpoint + `examLine` filter

Не обязательно создавать именно эти URL, если текущая API-структура использует другой паттерн. Важно отсутствие дублированной бизнес-логики.

## 7.1. Безопасность ответа API

До answer/reveal API не возвращает правильный ответ/разбор в обход существующих правил.

Не сломать существующее правило защиты answer leakage.

## 7.2. Невалидный номер

Для несуществующей линии:

- нормальный 404/empty-state;
- без server error;
- frontend не зависает.

---

# 8. Line progress

Предпочтительно рассчитывать line-progress из существующих attempts/questions, а не создавать отдельную дублирующую таблицу.

Минимальные метрики:

- attempted;
- correct;
- accuracy;
- lastAttemptAt;
- wrongQuestionRefs или эквивалент для `Повторить ошибки`.

Если extended answer оценивается не бинарно, использовать текущую модель scoring и не искажать её ради общей accuracy.

Если для line stats требуется новая БД-миграция — сначала доказать, что вычисление из существующих данных невозможно/неадекватно. Предпочтительно без новой постоянной дублирующей сущности.

---

# 9. Содержательное качество line pages

Каждая страница линии должна отвечать ученику на 5 вопросов:

1. Что от меня хотят в этом номере?
2. Какие знания нужны?
3. Как распознать тип задания?
4. Как пошагово решать?
5. На чём чаще всего теряют баллы?

Если страница просто показывает список связанных уроков — задача **не выполнена**.

## 9.1. Первая часть

Для линий первой части акцент:

- распознавание механики;
- быстрый алгоритм;
- ограничения формата ответа;
- типичные отвлекающие варианты;
- проверка результата.

## 9.2. Вторая часть

Для второй части:

- структура развёрнутого ответа;
- обязательные причинно-следственные звенья;
- сколько смысловых элементов надо раскрыть — только если это корректно для данного типа;
- критерии качества ответа;
- типичные неполные формулировки;
- примеры хорошего reasoning без копирования официальных ответов.

# 11. Поиск и deep links

Line pages должны иметь стабильные URL.

Пример допустимого route:

`#biology/line/23`

или существующий router-compatible эквивалент.

После refresh/deep-link страница должна открываться корректно, а не сбрасываться на главную Biology.

Back/forward browser navigation должна работать.

---

# 12. Mobile UX

Обязательный диапазон проверки: **360–430 px**.

Проверить:

- переключатель «По темам / По заданиям»;
- grid линий;
- длинные названия;
- badges первой/второй части;
- theory refs;
- алгоритмы;
- ловушки;
- кнопки тренировки;
- таблицы/графики;
- sticky/sidebar элементы;
- отсутствие горизонтального overflow.

Не уменьшать текст до нечитаемого размера ради помещения карточек.

---

# 13. Accessibility

Минимум:

- кнопки являются button/link по смыслу;
- keyboard focus виден;
- `aria-current`/эквивалент для активного режима, если применимо;
- SVG/image alt остаются содержательными;
- цвет не является единственным индикатором progress/state.

# 14. Автоматический аудит line-mode

Добавить скрипт, например:

`scripts/audit-biology-exam-lines.js`

и npm script:

`npm run audit:biology-exam-lines`

Проверки минимум:

1. нет duplicate line IDs;
2. номера валидны и упорядочены;
3. каждый `lessonRef` существует;
4. каждый `questionRef` существует;
5. вопрос в `questionRefs` соответствует номеру линии;
6. нет orphan question/lesson refs;
7. нет line page без theory links;
8. нет line page без practice, если линия должна иметь practice;
9. strategy не пустая;
10. commonTraps не пустые;
11. все line routes достижимы;
12. все line labels пользовательские, без технических audit markers;
13. no answer leakage regression;
14. mapping не создаёт дублированных lesson refs внутри одной линии.

Важно: этот аудит проверяет целостность, а не доказывает педагогическое качество.

# 15. Ручной аудит

После реализации открыть/проверить минимум:

- одну простую линию первой части;
- линию с таблицей/графиком;
- линию по эксперименту;
- линию со схемой/изображением;
- генетическую/расчётную линию;
- минимум две линии второй части.

Для каждой вручную проверить:

- маршрут понятен ученику с нуля;
- theory links релевантны;
- нет случайных нерелевантных уроков;
- алгоритм специфичен;
- ловушки реальные;
- practice действительно фильтруется по этой линии;
- правильный ответ не виден до answer/reveal;
- после ответа показывается нормальный разбор;
- deep link работает.

Если browser tool недоступен — честно написать это и выполнить максимально близкий programmatic/API/router smoke test. Нельзя писать `browser smoke passed`, если браузер не запускался.

# 18. Acceptance criteria

Задача принимается только если одновременно выполняется:

- Biology имеет два нормальных режима: `По темам` и `По заданиям ЕГЭ`.
- Все актуальные линии отображаются в порядке экзамена.
- Каждая line page не пустая.
- Каждая line page объясняет экзаменационную механику, а не только показывает темы.
- Связанные уроки открываются и являются существующими уроками, а не копиями.
- Тренировка реально фильтрует вопросы по линии.
- User progress по линии считается корректно.
- Reveal/answer security не сломаны.
- Mobile 360–430 px usable.
- Deep links работают.
- Нет orphan refs.
- Нет duplicate content.
- Нет служебного текста в UI.
- Все автоматические проверки зелёные либо конкретно перечислены реальные невыполненные проверки.

Целевые итоговые строки аудита:

```text
VISIBLE EXAM LINES = all current Biology lines
EMPTY LINE PAGES = 0
BROKEN LESSON REFS = 0
BROKEN QUESTION REFS = 0
ORPHAN LINE REFS = 0
ANSWER LEAK REGRESSIONS = 0
```

Не подменять эти критерии количеством строк кода.

# 20. Главное правило качества

Line-mode — это не каталог номеров.

Он должен позволить ученику выбрать конкретное задание ЕГЭ и пройти законченную цепочку:

**понять механику → выучить только нужную теорию → увидеть алгоритм → разобрать ловушки → решить задания → увидеть ошибки → повторить слабые места.**

Если эта цепочка не работает от начала до конца хотя бы для одной линии, работа по этой линии не считается завершённой.
