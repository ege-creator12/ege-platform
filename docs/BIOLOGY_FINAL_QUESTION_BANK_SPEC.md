# BIOLOGY — FINAL QUESTION BANK AUDIT & EXPANSION SPEC

## 0. Статус и цель

Это каноническое ТЗ для этапа после завершения основной теории по биологии.

Цель этапа — превратить текущий набор вопросов в действительно полный, качественный и экзаменационно полезный банк по биологии ЕГЭ-2027: без дыр по темам и механикам, без шаблонных вопросов, без бессмысленной гонки за количеством и без копирования чужих коммерческих банков.

На выходе ученик должен иметь возможность после изучения теории системно натренировать ВСЕ требуемые механики ЕГЭ по биологии, включая сложные задания второй части, работу со схемами, таблицами, графиками, экспериментами и расчётными/генетическими задачами.

Этот этап НЕ является работой над режимом «по линиям ЕГЭ» как интерфейсом и НЕ является этапом полноценных пробников. Здесь создаётся и проверяется сам банк, его метаданные, разборы и покрытие. Режим по линиям и пробники идут после этого.

# 1. Неподлежащие сокращению правила

1. Не считать качество банка по общему числу вопросов.
2. Не считать тему «закрытой» только потому, что в ней есть N вопросов.
3. Не использовать количество символов, число типов заданий или наличие тегов как доказательство качества.
4. Каждый вопрос должен проверять конкретное биологическое знание, навык или экзаменационную механику.
5. Все новые вопросы должны быть оригинальными.
6. Нельзя массово копировать задания, формулировки, варианты ответов или разборы из Решу ЕГЭ, NeoFamily, Foxford, Webium, Stepik и других коммерческих/публичных банков.
7. FIPI — первичный источник по структуре, навыкам и механикам экзамена. Вторичные ресурсы допустимы только для понимания типичных ловушек и разнообразия механик.
8. Текущая версия экзаменационной разметки проекта:
   - `exam_year = 2027`
   - `source_version = "FIPI EGE 2027 project"`
   Пока документы ФИПИ имеют статус проекта, не выдавать их за окончательно утверждённую спецификацию.
9. Не менять auth, пароли, сессии, unrelated DB-код и unrelated chemistry без реальной необходимости.
10. Сохранять существующие стабильные `question.id`, lesson/topic slugs и пользовательский прогресс везде, где вопрос можно исправить без удаления ID.
11. Если существующий вопрос ошибочен — исправить его на месте и зафиксировать это в аудите. Не плодить дубликат с новым ID только ради сохранения плохого старого вопроса.
12. Никаких `TODO`, `placeholder`, `пример`, `здесь будет вопрос`, служебных редакторских заметок или черновых объяснений в пользовательском контенте.
13. Не начинать с массовой генерации. Сначала обязательный BEFORE-аудит.

# 2. BEFORE-аудит текущего банка

До добавления новых вопросов создать фактическую карту текущего состояния банка.

Создать/обновить:

`content/biology/QUESTION_BANK_AUDIT.md`

Аудит должен быть основан на реальных данных `course.json` и связанных сущностях, а не на предположениях.

Для каждого раздела, темы и урока зафиксировать:

- section id/title;
- topic id/title;
- lesson id/slug/title;
- количество существующих вопросов;
- типы вопросов;
- difficulty;
- exam lines / mechanics;
- наличие изображений/таблиц/графиков/экспериментов;
- наличие заданий с развёрнутым ответом;
- наличие детальных explanations/rubrics;
- проблемы качества;
- пробелы по механикам;
- итоговый BEFORE-статус.

Отдельно построить матрицу:

`exam line / mechanic -> темы -> существующие вопросы -> качество -> пробелы`

Не ограничиваться прямыми счётчиками. Для выборки существующих вопросов провести ручной содержательный review.

Минимально вручную проверить:

- все существующие задания второй части;
- все генетические задачи;
- все задачи по молекулярной биологии/цитологии с расчётами;
- все задания на эксперимент;
- все задания на графики/таблицы;
- все задания с изображениями;
- не менее нескольких вопросов каждого типа в каждом из 7 макроразделов биологии.

Обязательные проверки BEFORE:

- дубликаты ID;
- ссылки на отсутствующие lesson/topic;
- duplicate question refs;
- вопросы без ответа;
- вопросы без объяснения, где объяснение требуется;
- вопросы с противоречием prompt/answer;
- вопросы, где правильный ответ случайно виден в prompt, подписи картинки, alt или соседнем блоке;
- бессмысленные/очевидные distractors;
- почти дословные дубли;
- редакторский мусор;
- невозможные/неоднозначные формулировки;
- вопросы, где допустимо несколько ответов, но система принимает только один;
- устаревшие экзаменационные метки.

В конце BEFORE-аудита дать не общий процент, а конкретный список дефицитов, которые нужно закрыть.

# 4. Покрытие экзаменационных механик

Не привязывать качество только к типу UI-поля (`multiple_answer`, `matching` и т.п.). Одна и та же механика может требовать разных мыслительных действий.

Банк обязан содержать достаточное разнообразие следующих механик там, где они релевантны текущему экзамену:

- multiple answer;
- matching;
- sequence;
- table completion/interpretation;
- image recognition/analysis;
- graph analysis;
- experiment analysis;
- short answer;
- extended answer;
- biological process analysis;
- text analysis;
- quantitative/biological calculation;
- genetics problem;
- molecular/cytological calculation;
- structure-function explanation;
- cause-effect explanation;
- compare/contrast;
- prediction of consequences;
- methodological critique of experiment.

Для каждой экзаменационной линии/механики, имеющейся в текущем `exam_lines`, после этапа должно быть видно:

- какие темы её тренируют;
- какие вопросы относятся к ней;
- есть ли easy/medium/hard варианты там, где это педагогически разумно;
- есть ли качественный разбор;
- есть ли достаточное разнообразие контекста.

Не создавать искусственно easy/medium/hard для механик, где это делает вопрос нелепым. Difficulty должна отражать реальную когнитивную сложность.

# 5. Требования к качеству вопросов первой части

Каждый вопрос должен:

1. Иметь один однозначно интерпретируемый prompt.
2. Не содержать лишней информации, которая случайно выдаёт ответ.
3. Проверять биологию, а не чтение угадываемого шаблона.
4. Использовать корректную современную школьную терминологию.
5. Иметь валидный правильный ответ.
6. Для вариантов ответа — иметь правдоподобные distractors, основанные на реальных типичных ошибках.
7. Не использовать очевидные мусорные distractors вида «митохондрия — орган пищеварительной системы» в сложных вопросах.
8. Не делать правильный вариант систематически самым длинным/точным.
9. Не создавать грамматические подсказки.
10. Не дублировать почти дословно соседний вопрос с заменой одного существительного.

Для `matching`:

- элементы должны принадлежать одной логике;
- количество и структура вариантов должны соответствовать механике;
- не должно быть неоднозначного соответствия, если это не предусмотрено форматом.

Для `sequence`:

- последовательность должна иметь биологически однозначный порядок;
- если возможны параллельные процессы, формулировка должна задавать конкретный критерий порядка.

Для image-задач:

- изображение должно реально помогать/быть необходимым для решения;
- подпись/alt не должны выдавать ответ;
- все метки читаемы на мобильном;
- схема не должна быть декоративной карточкой вместо биологического объекта.

# 6. Требования ко второй части

Задания с развёрнутым ответом — критически важная часть этапа.

Нельзя делать их как один общий вопрос с абзацем «пример ответа».

Каждое качественное задание второй части должно иметь:

- чёткую формулировку;
- ожидаемые смысловые элементы;
- rubric/scoring points;
- допустимые альтернативные формулировки там, где они реально эквивалентны;
- подробный разбор причинно-следственной логики;
- типичные ошибки;
- пояснение, за что теряется балл;
- отсутствие требований к несущественной формулировке, если биологический смысл верен.

Развёрнутые задания должны включать разные классы:

- анализ эксперимента;
- анализ схемы/рисунка;
- анализ биологического процесса;
- сравнение объектов;
- объяснение причин и следствий;
- прогноз результата изменения условия;
- работа с текстом/данными;
- молекулярная биология;
- генетика;
- цитология;
- физиология человека;
- ботаника/зоология;
- эволюция;
- экология.

Не концентрировать всю сложную практику только в генетике и человеке.

---

# 7. Генетика, молекулярные задачи и расчёты — отдельный контроль качества

Для всех расчётных задач создать программные или детерминированные sanity-checks там, где это возможно.

Проверять:

- арифметику;
- проценты;
- количество нуклеотидов;
- число водородных связей только при корректно заданных данных;
- длину/массу молекул только если используются школьные допущения, явно принятые в задаче;
- число аминокислот;
- рамку считывания там, где она требуется;
- хромосомный набор;
- количество молекул ДНК;
- генетические вероятности;
- рекомбинацию;
- сцепление;
- соответствие генотипов фенотипам.

Не использовать спорные коэффициенты или физико-химические константы без явного школьного контекста.

Каждая задача должна быть решаема из данных prompt без скрытых предположений.

---

# 8. Эксперименты, графики и таблицы

Каждый эксперимент должен содержать реалистичный объект и измеримый результат.

Проверить, чтобы ученик мог однозначно определить:

- исследуемый фактор;
- независимую переменную;
- зависимую переменную;
- контроль;
- условия, которые надо удерживать постоянными;
- ожидаемый график/результат;
- корректность вывода.

Графики:

- оси подписаны;
- единицы указаны, если нужны;
- масштаб не вводит в заблуждение;
- данные согласованы с ответом;
- не выдавать ответ названием графика.

Таблицы:

- заголовки понятны;
- данные непротиворечивы;
- число значащих цифр не создаёт ложной точности;
- вопрос требует анализа, а не простого переписывания одной клетки, если заявлена сложная механика.

Если data/graph генерируются программно — сохранять детерминированность, чтобы тесты были стабильными.

---

# 9. Explanation и feedback

Каждый вопрос должен иметь объяснение достаточной глубины для самостоятельного обучения после ошибки.

Плохое explanation:

> Правильный ответ — 2, потому что это митохондрия.

Хорошее explanation:

- называет ключевой признак;
- объясняет механизм;
- связывает его с правильным ответом;
- при необходимости объясняет, почему типичные альтернативы неверны;
- показывает экзаменационную ловушку;
- для расчёта показывает ход решения;
- для второй части показывает смысловые элементы.

Не дублировать prompt в explanation.

Не вставлять редакторские фразы вроде «после ручного review», `verified`, `EGE_REQUIRED`, `qualityBasis` в пользовательский текст.

---

# 10. Семантические дубли и шаблонность

Автоматическая проверка точных строк недостаточна.

Нужно выявлять:

- одинаковый смысл с перестановкой слов;
- один шаблон, размноженный на 20 объектов;
- одинаковую правильную логику с косметически заменёнными числами;
- одинаковые distractors;
- повторяющиеся introductions;
- повторяющиеся explanation-фразы.

Допустимо иметь несколько задач на одну механику, если они действительно проверяют разные случаи, контексты или уровень переноса навыка.

Не удалять полезные вариации только потому, что они относятся к одной теме.

---

# 11. Баланс сложности

Difficulty нельзя назначать по длине текста.

Ориентиры:

### Basic
- прямое применение одного знания;
- простое распознавание;
- один шаг логики.

### Medium
- комбинация 2–3 знаний;
- интерпретация схемы/данных;
- сравнение;
- применение знания в новом контексте.

### Hard
- многошаговая причинно-следственная логика;
- сложный эксперимент;
- интеграция нескольких тем;
- полноценная задача второй части;
- генетическая/молекулярная задача с несколькими этапами;
- анализ нетривиальных данных.

Не завышать сложность за счёт туманной формулировки.

---

# 12. Количество как guardrail, а не KPI

Не ставится цель «любой ценой сделать X вопросов».

Сначала определить реальный дефицит по каждой теме и механике.

После расширения банк должен иметь достаточно вариативности, чтобы ученик не запоминал один шаблон после 1–2 вопросов.

Практический guardrail:

- ни одна обязательная экзаменационная механика не должна быть представлена единственным вопросом;
- ключевые многовариантные механики должны иметь несколько независимых контекстов;
- сложные области (генетика, молекулярная биология, эксперимент, физиология, экология с данными) должны иметь заметно более богатую практику;
- каждая крупная тема должна содержать не только basic-вопросы;
- в каждом из 7 макроразделов должны присутствовать задания, требующие объяснения, а не только выбора ответа.

Если после качественного покрытия получится существенно меньше/больше ожидаемого числа — это допустимо. В отчёте объяснить почему.

---

# 13. Метаданные и совместимость

Для каждого вопроса проверить/добавить корректные поля, которые поддерживает текущая схема проекта:

- stable id;
- lesson reference;
- topic/section reachability через lesson;
- question type;
- difficulty;
- exam line(s);
- mechanic/skill tags, если предусмотрены схемой;
- prompt;
- answer;
- explanation;
- media reference;
- rubric/scoring metadata для extended answer, если поддерживается;
- source/provenance metadata для оригинального контента, если предусмотрено.

Не вводить новую параллельную модель данных без необходимости.

Если текущая схема не позволяет хранить важную информацию для качественного разбора, расширение должно быть минимальным, обратнос совместимым и покрытым тестами.

Существующий answer/reveal flow не ломать:

- правильный ответ не должен утекать до ответа/reveal;
- reveal даёт 0 XP;
- попытка фиксируется корректно;
- повторный reveal идемпотентен;
- human-readable review сохраняется.

---

# 14. Медиа

Использовать существующие качественные SVG, где они подходят.

Новые SVG делать только когда вопрос реально требует изображения.

Каждый новый SVG:

- оригинальный;
- биологически корректный;
- читаемый;
- адаптирован под светлый текущий интерфейс;
- имеет `<title>` и `<desc>`;
- имеет `viewBox`;
- корректно масштабируется на мобильном;
- не содержит ответа в имени/alt/описании, если это ломает вопрос;
- лежит в предсказуемой папке;
- проходит существующий media resolver.

После недавних багов обязательно провести фактический audit путей всех media refs, используемых вопросами.

Запрещено оставлять пользовательский fallback «Схема временно недоступна» для нового обязательного вопроса как приемлемый результат этапа.

---

# 15. Автоматизированный аудит банка

Создать отдельный скрипт, предпочтительно:

`scripts/audit-biology-question-bank.js`

и npm script, например:

`npm run audit:biology-questions`

Аудит должен завершаться non-zero при критических проблемах.

Минимальные автоматические проверки:

- уникальность question IDs;
- все lesson refs существуют;
- нет orphan questions;
- нет duplicate refs;
- валидные типы;
- валидные difficulty;
- непустой prompt;
- валидный answer;
- explanation присутствует там, где обязателен;
- extended answer имеет необходимую структуру/rubric, если схема это поддерживает;
- media refs существуют;
- referenced SVG валиден как текстовый SVG;
- нет запрещённых editor markers;
- нет точных дубликатов prompt;
- нет очевидных exact duplicate explanation;
- все exam line refs валидны;
- каждая обязательная механика имеет покрытие;
- JSON/schema consistency.

Автоматический аудит НЕ имеет права объявлять вопрос качественным только потому, что все поля заполнены.

---

# 16. Ручной AFTER-аудит

После добавления/исправления банка провести содержательный AFTER-review.

Обязательно вручную проверить выборки:

- не менее 15 новых/изменённых вопросов по клетке/молекулярке;
- не менее 15 по генетике;
- не менее 15 по ботанике/зоологии;
- не менее 15 по человеку;
- не менее 10 по эволюции;
- не менее 10 по экологии;
- все новые задания extended answer;
- все новые эксперименты;
- все новые графики/таблицы;
- все новые расчётные задачи;
- все вопросы с новым SVG.

Если в выборке обнаружена систематическая ошибка, не ограничиваться выбранными вопросами — проверить весь класс вопросов с тем же шаблоном/генератором.

В `QUESTION_BANK_AUDIT.md` зафиксировать:

- BEFORE;
- что исправлено;
- что добавлено;
- AFTER;
- какие вопросы были вручную просмотрены;
- какие проблемы нашли в процессе;
- что осталось вне scope.

# 17. Регрессионные тесты

Обязательные команды:

```bash
npm run audit:biology-theory
npm run audit:biology-questions
npm run check
npm test
npm run import-content -- --dry-run

git diff --check
node --check server.js
node --check public/app.js
node --check public/content-sanitizer.js
```

Если некоторые файлы/скрипты отсутствуют после выбранной реализации — адаптировать команды честно, но не писать, что проверка прошла, если она не запускалась.

Дополнительно:

- проверить импорт в чистую временную БД;
- проверить сохранение существующих question IDs;
- проверить answer/reveal на нескольких типах;
- проверить изображения;
- проверить вопросы на мобильной ширине 360–430 px, если browser доступен;
- если browser отсутствует — явно написать это в финале и выполнить программный/DOM-equivalent smoke там, где возможно.

# 18. Что НЕ делать в этом этапе

Не делать сейчас полноценно:

- отдельный UI режима «Задание №N»;
- генератор полного варианта ЕГЭ;
- таймер полного пробника;
- новую систему аккаунтов;
- новую систему оплаты;
- большой redesign;
- химию.

Можно делать только минимальные инфраструктурные изменения, необходимые самому банку и его корректному отображению.

---

# 19. Acceptance criteria

Этап считается завершённым только если одновременно выполнено следующее:

1. Выполнен реальный BEFORE-аудит банка.
2. Все 7 макроразделов имеют качественную практику.
3. Все обязательные текущие exam lines/mechanics имеют покрытие.
4. Нет orphan/duplicate/broken refs.
5. Нет битых обязательных media refs.
6. Нет служебного текста в пользовательских вопросах/разборах.
7. Генетические и молекулярные расчётные задачи проверены.
8. Эксперименты методически корректны.
9. Графики/таблицы согласованы с ответами.
10. Extended answers имеют реальные смысловые элементы и разборы.
11. Новые вопросы оригинальны.
12. Нет массовой шаблонной генерации, замаскированной заменой терминов/чисел.
13. Выполнен ручной AFTER-review.
14. Все автоматические тесты зелёные либо честно перечислены технически недоступные проверки.
15. Существующий прогресс/ID сохранён максимально возможно.
16. Финальный отчёт не использует число вопросов как единственное доказательство качества.

---

# 20. Финальный отчёт Codex

В конце задачи дать отчёт строго по разделам:

## A. BEFORE
- сколько вопросов было;
- распределение по разделам/типам/difficulty;
- реальные обнаруженные пробелы и ошибки.

## B. Исправленные старые вопросы
- количество;
- категории ошибок;
- какие ID сохранены.

## C. Новые вопросы
- количество только как справочная метрика;
- распределение по 7 разделам;
- распределение по механикам;
- сколько extended/experiment/graph/table/image/genetics/calculation.

## D. Exam coverage
- таблица line/mechanic -> темы -> количество качественных вариантов -> статус.

## E. Manual review
- какие выборки просмотрены;
- какие ошибки нашли;
- какие системные исправления из этого последовали.

## F. Media
- новые/использованные SVG;
- broken refs = 0;
- как проверено.

## G. Tests
- каждая реально выполненная команда и результат;
- отдельно перечислить то, что не удалось выполнить.

## H. Remaining risks
- честно перечислить всё, что ещё требует следующего этапа.

# 21. Главный педагогический критерий

Финальный вопрос для каждого участка банка:

> Если ученик изучил нашу теорию, затем прорешал этот банк и внимательно разобрал ошибки — получил ли он практику, достаточную для уверенного решения соответствующих заданий ЕГЭ, включая сложные варианты, без необходимости уходить на другой сайт из-за дыр в механиках?

Если ответ «нет» — участок банка не завершён, даже если автоматический audit зелёный.
